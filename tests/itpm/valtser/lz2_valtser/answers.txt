2.1. Використання окремих гілок для виконання завдань (Feature Branches / Git-flow):
Окремі гілки дозволяють ізолювати розробку нових функцій, експериментів чи виправлення багів від стабільної кодової бази (main / staging / develop). Це гарантує:
- незалежну паралельну роботу декількох розробників над різними задачами без конфліктів у коді;
- збереження працездатності головної гілки проєкту;
- легкість відкату (revert) змін у разі невдалої реалізації фічі без шкоди для решти системи.

2.2. Захист гілок від злиття без проходження код-рев'ю (Branch Protection Rules & Code Review):
Захист гілок (наприклад, заборона прямого пушу в main/develop та обов'язковий Pull Request з мінімум 1-2 апрувами старших інженерів) необхідний для:
- запобігання випадковому потраплянню неякісного, сирого або шкідливого коду у релізний білд;
- обміну знаннями в команді та дотримання єдиного код-стайлу проєкту (clean code, SOLID, архітектурні патерни);
- виявлення архітектурних прорахунків, проблем із безпекою та логічних помилок на ранньому етапі, ще до етапу тестування.

2.3. Для чого необхідний CI/CD процес та його значення в управлінні проєктами:
CI/CD (Continuous Integration / Continuous Deployment) — це автоматизація процесів збірки, статичного аналізу (лінтери), виконання автоматизованих тестів та розгортання ПЗ на сервери.
Значення в управлінні IT-проєктами:
- Скорочення Time-to-Market: швидкий випуск оновлень для клієнтів.
- Раннє виявлення дефектів (Shift-Left Testing): автотести запускаються автоматично при кожному пуші/Pull Request, не дозволяючи зламати регресійну функціональність.
- Зниження рутинного навантаження на QA та DevOps фахівців.
Приклад існуючого додатку: 
Сервіс таксі або доставки (наприклад, Uber / Bolt). Для таких сервісів критично важливі CI/CD пайплайни, оскільки щоденно вносяться десятки змін різними командами (геолокація, платіжні шлюзи, тарифні сітки). Якщо при виправленні алгоритму розрахунку знижки зламається модуль авторизації або приймання банківських карток, без автоматизованого CI/CD пайплайну цей збій потрапить у прод і призведе до мільйонних збитків компанії та втрати клієнтів протягом перших 10 хвилин. Автоматичний пайплайн у GitHub Actions запускає e2e-тести і миттєво блокує злиття коду, який не пройшов верифікацію.
